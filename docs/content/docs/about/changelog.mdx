## Unreleased

- **The shell hook records into the project whose session is open.** `treeship hook post` (installed by `treeship install` into the shell) used the store an exported `TREESHIP_CONFIG` named, not the project's `.treeship/config.json` beside the `config.yaml` it had found, so a session started with `--config` in the project and the hook's receipts could end up in different stores. For the shell hook only, the precedence is now: an explicit `--config`, then the project's own config when a session is active in that project, then `TREESHIP_CONFIG`, then discovery. The project config is opened as a discovered config, so a cloned repository's `config.json` gets every discovery check (stores inside its own `.treeship`, no `extends` outside the home, no linked `.treeship`) before any key is used.
- **The lockfile check also compares the package's own version.** A `package-lock.json` whose root version lags `package.json` (the OpenClaw plugin's read 0.10.3 at 0.31.10) fails `scripts/check-lockfile-sync.py`; the plugin's lockfile is refreshed, `scripts/lockfile-pin.py` stamps those fields at release time, and the plugin is in `release.sh`'s lockfile lists.
- **Clippy runs on wasm32 in CI (PKG-3).** `std::fs::File` has no `Drop` on that target, so an explicit `drop(lock_file)` in the keystore migration failed the lint there; the handle is bound to the function's scope instead, and the feature-matrix job lints core-wasm on wasm32 with warnings denied.
- **`wrap` exits with the wrapped command's code in every format.** `--format json wrap -- <cmd>` returned 0 when the command failed, with the code only inside the document, so `treeship --format json wrap -- npm test && deploy` deployed after failing tests; text mode was right. Every format, and `--quiet`, now propagates the code (128 + signal for a signal death).
- **`--format json` leaves exactly one document on stdout.** Warnings (`{"status":"warning",…}`) go to stderr in JSON mode, like errors; 0.31.10 printed a warning document before the result on `attest action --v2` outside the grant's scope and on `trust add --replace`, and parsers failed with "Extra data".
- **`merkle publish` and `checkpoint --publish` report what reached the hub.** `--format json merkle publish` wrote nothing on success; it now prints the hub checkpoint id, proofs published, local-only artifacts skipped, the consistency proof's outcome and the share URL. `checkpoint --publish --format json` carries the same under `publish`, so a caller can tell the checkpoint was published; text mode is unchanged. The `checkpoint` hint names the whole root, not a truncated one `merkle verify` would reject.
- **A registered predicate that fails its schema exits 4.** `attest receipt --kind memory.write.v1` (or any registered kind) with a payload that fails validation is the call refused as written, exit 4 as the exit-code table says; 0.31.10 exited 1. Same for the session and judge paths that validate a predicate.
- **Countersign hints are complete.** `session answer-challenge` and `session join` (text and `countersign_hint` in JSON) name every flag the host needs: `--challenge`, `--challenge-issued-at` and `--challenge-response`, and `--pending <file>` in place of the participant id when the join was written with `--out` for a host on another machine. The host used to learn the missing flags from exit 4.
- **`match --class` and `room create --delegate` validate their arguments.** An unknown class exits 4 before the hub is asked (it used to answer with an empty match set); a delegate that is not an Ed25519 public key exits 4 instead of being sealed into the room, and a bare base64url key is stored in the canonical `ed25519:` form.
- **`agents remove` of a card that is not there is an error**, not "removed" with exit 0.
- **A second `init` says what is true.** In a directory with no workspace of its own while a global one exists, the message names the global workspace and how to create a project one (it no longer suggests regenerating the global identity); when the global workspace lives in the current directory it says so.
- **`hub open` on a self-hosted hub mints no token and points at the hub's JSON workspace.** Such a hub has no workspace page; the command used to mint a share token and paste it into a treeship.dev URL that does not exist for that hub. It now prints `<endpoint>/v1/workspace/<dock>` and mints nothing. The hosted hub (a treeship.dev endpoint, judged by a real URL parser) is unchanged. `hub attach --endpoint` drops a trailing slash, which used to produce `//v1/dock/challenge` and a 404.
- **`init --help` no longer says the key is tied to the machine.** The key is encrypted with a seed file kept beside the keystore and travels with `.treeship/`, as SECURITY.md says.
- **A release no longer tags a red main.** The lockfile check (`scripts/check-lockfile-sync.py`) failed on `main` between the version bump merging and the packages reaching npm, because the installed lockfile entries could not yet name a version that had no tarball, so every release was tagged on a failing commit. An installed entry that lags the release in flight (the version in `packages/core/Cargo.toml`) is now a warning while that exact version is not on the registry, and fails again the moment it is published, which is what forces `scripts/release.sh refresh-lockfiles`. The declared-range half of the check, the release-branch window, and the behaviour when the registry cannot be reached are unchanged. The gate has unit tests with the registry lookup stubbed.

## 0.31.9 (2026-09-25)

- **A lifted halt stays lifted, whatever local file is rolled back.** The 0.31.8 fix read the store through `index.json`, an unsigned cache in the same directory as the halt marker; restoring both re-armed a halt while its signed lift sat on disk. The lookup now scans the record files and honours a halt, or a lift, only when its envelope verifies under the workspace key; the record's unsigned `key_id` is not consulted. `halt list` says which reason applies (`lifted by art_…`, or not signed here) instead of "no signed artifact" for both. - **`verify --full` fails what `verify` fails.** Full mode never received the invalid-mandate fix: it opened with a green chain line, closed with three green summary rows, and exited 0 on an artifact the default mode exits 1 on. - **`attest receipt --kind list` stands alone**, without `--system`.

- **Security: Rekor anchoring works, and only a verified anchor counts (TS-2026-003).** `<!-- claims:rekor-artifact-anchoring -->` The hub's Rekor submissions had never succeeded. Treeship signatures are unpadded base64url, which Rekor rejects, and the `hashedrekord` type cannot verify plain Ed25519 anyway. The failure was swallowed and the CLI printed `rekor: pending`. The hub now submits a `dsse` entry, which Sigstore's staging log accepts, and returns `rekor.status` (`anchored`, `failed`, `skipped`) with a reason and the full log entry. Re-pushing an unanchored artifact retries it. Separately, `verify --max-unwitnessed` took witness times from `Record.anchors[].observed_at` and claimed times from `Record.signed_at`. Now an anchor counts only if its Rekor entry verifies offline: signed entry timestamp, RFC 6962 inclusion proof, signed checkpoint, and binding to this artifact's payload and signature. Its time is Rekor's `integratedTime`. Claimed times come from each statement's signed `timestamp`. The gate runs in every output mode. JSON gains `anchoring` (`coverage`, a `tally` of verified, claimed-unverified, failed and rejected anchors, and `gate`). Existing anchors carry no proof and now report as claimed but unverified.
- **Packages and bundles carry their Rekor proofs.** `session close` writes each sealed artifact's proofs to `anchors/<id>.json`, and `package verify` adds an `anchoring` row: it passes with the Rekor time span, fails when a stapled proof does not hold or is for another artifact, and warns on a log you have not pinned. A package without proofs has no row, so existing verdicts are unchanged. `bundle export` includes proofs under `anchors`, and `bundle import` merges them with the local store's instead of replacing its anchors.
- **`transparency_log` trust roots.** The Sigstore public-good Rekor key is built in. `trust add <label> @rekor.pub --kind transparency_log` pins another log, such as a private Rekor, and replaces the built-in key rather than adding to it. - **The hub no longer stores a checkpoint's caller-supplied `rekor_index`.** It was saved and served back verbatim, so any dock could attach an arbitrary index to its checkpoint. It is null until the hub anchors checkpoints itself.

Every artifact signed in the workspace during the session is now sealed, after the chain, and marked `unchained: true` in the receipt so a verifier can tell a linked step from a loose one; the close output lists them (`sealed_unchained` in JSON, a warning and hint in text) and `package verify` reports them as `chain_completeness`. `attest action` prints a hint when a session is active and no `--parent` was given.
- **The MCP bridge reports signing failures (AUD-33, P2).** A failed `attest`, `session event` or `session start` inside the bridge was caught and dropped, so a tool call with no receipt looked like one that was never recorded. The bridge now writes `[treeship] <what> failed: <reason>` to stderr on every failure and, under `TREESHIP_STRICT=1`, fails the tool call instead of proceeding unrecorded.
- **Docs: the Verifiable Intent page says which draft.** "Shipped in 0.31" is qualified as shipped against the v0.1 draft, the wording the CLI uses (QA TS-007). The commerce quickstarts start from `git clone` of the reference (QA TS-008).

## 0.31.1 (2026-09-08)

- **treeship-commerce: the order receipt no longer forks the chain (QA TS-002, P0).** `order_placed` signed the host's order onto the hand-off receipt. The checkout result, which also follows the hand-off, became a branch off the path the session seals, so it was signed, verifiable on its own, and absent from the package, while `package verify` reported a clean package. The order now chains onto the recorder's head and names the hand-off in `meta.handoff`; `attest_at_handoff` does the same. A test asserts every receipt a recorder writes is on the sealed chain.
- **`session close` names unsealed branches (QA TS-002).** Signed artifacts whose parent is on the sealed chain but which are not on it themselves are listed in the close output (`unsealed_branches` in JSON, a warning in text) instead of vanishing silently.
- **The demos run on a clean machine (QA TS-001, TS-004).** `demo` and `demo_merchant` construct the SDK with `bot_mode=True`, so the CLI is resolved (PATH, cache, then the matching release) rather than assumed; a missing workspace or CLI prints a one-line remedy instead of a traceback; a session a previous run left open is closed with a summary that says so, so a second run works.
- **The SDK warns when the CLI is on another release line (QA TS-003).** Once per client, on the first call: `treeship --version` against the SDK's own version, a `RuntimeWarning` naming both and the upgrade command.
- **Quickstarts use the project-local init (QA TS-006).** `treeship init --config .treeship/config.json` in every commerce quickstart. Bare `treeship init` refuses when a global workspace already exists and the current directory is not it (that guard predates 0.31; it was the first command in the quickstarts that was wrong).
- **`bootstrap.py` docstring matches `bootstrap_cli` (QA TS-005):** the entry point prints the binary path, or the JSON result with `--json`.
