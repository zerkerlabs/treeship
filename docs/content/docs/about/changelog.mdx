## Unreleased

- **The human's decision on a judgement is its own signed artifact.** An escalated judgement used to go quiet: nothing recorded who decided, what, or when. `treeship judge --resolve <judgement> --by human://alice --decision allow|deny|route` signs a `judgement.resolution.v1` receipt under the decider's URI, with the judgement as its subject, chained onto the session, recording what it `overrides` when it contradicts the judge. `package verify`'s `judgements` row pairs resolutions with escalations and reports an escalation with no resolution in the package as open (a warning), and names any judge decision a resolution overrode. A machine field saying "a human overrode this" would be the self-report a receipt exists to replace; a receipt under the decider's name is a claim the decider made.
- **The receipt commits to the judge's exact answer.** A judgement is signed by the caller, so on its own it is the caller's claim about what the judge said. `judgement.v1` now carries `response_digest`, the hash of the raw response bytes as received, and `judge.request_id`, the judge's own id for the answer when it gives one (the Jev adapter passes `x-typesafe-request-id` through); a fabricated answer has to come with a body that hashes to the digest, and a judge that keeps its responses can be asked about the id. Judge co-signing is the next step and the docs say so. `--state-out` writes the canonical state the receipt's `state_digest` commits to, for a verifier who re-runs the rules judge or checks what an outside judge was shown.
- **`TREESHIP_JUDGE_STRICT=1`** makes the Claude Code gate escalate a call the judge could not answer to the operator instead of letting it proceed with a note; the judge page says why the default fails open (the card already allowed the call) and why `treeship judge` itself never does.
- **`judgement.v1` carries the decision contract.** `treeship judge --contract ticket-router@3` records `contract: {id, version}` in every receipt: the versioned definition of state, question, options and threshold, separate from the application's version, so a change to the question is reviewable like a code change.
- **Jev in the judge slot.** `examples/judge-adapters/jev` puts TypeSafe's Jev behind the judge contract: a dependency-free adapter that speaks the contract on one side and `POST /v1/systemone` on the other, pins the model version so the receipt names one, and marks every answer `replayable: false`. Tested in CI against a mock of TypeSafe's documented request and response shapes (all three primitives mapped, an unavailable judge as an error, the `judgements` row naming the model). An independent implementation against the published API, not run against the live service. New integration page, systems registry row, and the post "Any judge, one receipt".

## 0.31.9 (2026-09-25)

- **A lifted halt stays lifted, whatever local file is rolled back.** The 0.31.8 fix read the store through `index.json`, an unsigned cache in the same directory as the halt marker; restoring both re-armed a halt while its signed lift sat on disk. The lookup now scans the record files and honours a halt, or a lift, only when its envelope verifies under the workspace key; the record's unsigned `key_id` is not consulted. `halt list` says which reason applies (`lifted by art_…`, or not signed here) instead of "no signed artifact" for both. (Retest 0.31.8, T20.)
- **`verify --full` fails what `verify` fails.** Full mode never received the invalid-mandate fix: it opened with a green chain line, closed with three green summary rows, and exited 0 on an artifact the default mode exits 1 on. The summary now carries an `authority` row, the `AUTHORITY INVALID` banner follows it, `--require-authority` is honoured, and every failure exits 1 in every mode. (Retest 0.31.8.)
- **`attest receipt --kind list` stands alone**, without `--system`.

- **Security: Rekor anchoring works, and only a verified anchor counts (TS-2026-003).** The hub's Rekor submissions had never succeeded. Treeship signatures are unpadded base64url, which Rekor rejects, and the `hashedrekord` type cannot verify plain Ed25519 anyway. The failure was swallowed and the CLI printed `rekor: pending`. The hub now submits a `dsse` entry, which Sigstore's staging log accepts, and returns `rekor.status` (`anchored`, `failed`, `skipped`) with a reason and the full log entry. Re-pushing an unanchored artifact retries it. Separately, `verify --max-unwitnessed` took witness times from `Record.anchors[].observed_at` and claimed times from `Record.signed_at`. Both are unsigned values in files the operator controls, so an edited record passed any policy. It also ran only in text output: `--format json` and `--full` ignored it and exited 0. Now an anchor counts only if its Rekor entry verifies offline: signed entry timestamp, RFC 6962 inclusion proof, signed checkpoint, and binding to this artifact's payload and signature. Its time is Rekor's `integratedTime`. Claimed times come from each statement's signed `timestamp`. The gate runs in every output mode. JSON gains `anchoring` (`coverage`, a `tally` of verified, claimed-unverified, failed and rejected anchors, and `gate`). Existing anchors carry no proof and now report as claimed but unverified.
- **Packages and bundles carry their Rekor proofs.** `session close` writes each sealed artifact's proofs to `anchors/<id>.json`, and `package verify` adds an `anchoring` row: it passes with the Rekor time span, fails when a stapled proof does not hold or is for another artifact, and warns on a log you have not pinned. A package without proofs has no row, so existing verdicts are unchanged. `bundle export` includes proofs under `anchors`, and `bundle import` merges them with the local store's instead of replacing its anchors.
- **`transparency_log` trust roots.** The Sigstore public-good Rekor key is built in. `trust add <label> @rekor.pub --kind transparency_log` pins another log, such as a private Rekor, and replaces the built-in key rather than adding to it. This is a new trust kind: a `trust_roots.json` containing one will not load in 0.31.8 or earlier.
- **The hub no longer stores a checkpoint's caller-supplied `rekor_index`.** It was saved and served back verbatim, so any dock could attach an arbitrary index to its checkpoint. It is null until the hub anchors checkpoints itself.

## 0.31.8 (2026-09-24)

- **An invalid mandate fails `verify` by default.** An action whose own mandate did not authorize it (out of scope, expired, wrong holder, revoked) verified as `outcome: pass, failed: 0`, exit 0, with `authority_ok: false` two fields down; only `--require-authority` changed the exit code, and even then the JSON said pass. Now the top line is `AUTHORITY INVALID`, JSON reports `outcome: fail` with the verdicts counted in `failed` and named in `authority_failed`, and the exit code is 1 with no flag. `--require-authority` remains the stricter mode (no mandate, or an uncheckable layer, also fails). (Retest 0.31.7, finding 30.)
- **A signed lift outlives a restored marker.** Restoring a saved halt marker file after `halt --lift` re-armed the halt: the gate read the marker and never looked for the lift. `halt list`, the gate's source, now treats a marker as an order only when no signed lift names its halt; a marker outliving its lift is reported `lifted_by: <the lift>`, not honoured, and removed. (T20.)
- **The payload's own `schema` must be the kind.** `attest receipt --kind confirmation` signed an `evaluation.v1` payload with a verdict outside its vocabulary, because validation dispatched on the flag alone. A payload naming a registered predicate as its `schema` is now refused under any other kind. `--kind list` prints the registry, and `--help` names every registered predicate (a test keeps the two in step). (31, 32.)
- **`grant issue --expiry` takes a duration** (`30d`, `12h`, `45m`), and the help examples use one; the fixed example date had fallen into the past and refused when pasted. (33.)
- **`verify --full` wraps a long authority reason** across box lines instead of cutting it mid-word at the frame. (34.)
- **A workspace moved to another path can still sign.** The keystore's primary key binds the store's path, so a workspace restored elsewhere (a fresh container, another CI checkout, a backup) could verify but never sign, and an interrupted session there could never be closed. The store now records the canonical path it decrypts under in `keys/keystore.origin`; opened at a new path, it decrypts under the recorded one and rewraps. For a store with no origin file, `TREESHIP_KEYSTORE_ORIGIN=<previous path>` once does the same, and the MAC error says so. (N1.)
- **`bundle import` names both pins** for an unpinned signer and says which applies to an agent's own key and which to the ship key, instead of guessing one from the id. (N2.) `trust add` prints that its store is machine-wide, whatever `--config` says, and the trust page says how to isolate ships when testing.
- **`treeship judge --enforce`** exits 2 on `deny` and 3 on `ask`, for shell gates; without it the exit code says only whether the judge answered, and the judge page says why that is the default.

## 0.31.7 (2026-09-23)

- **The `judgements` row reads a yes/no answer both ways.** It flagged every judgement "acted at noul 0.000 below its threshold", which is the rules judge answering no to "unsafe?" and the caller proceeding: exactly what the bar asked for. The row now flags an effect that contradicts the side of the threshold the answer fell on (a yes allowed, a no refused) or a judgement with no bar; a confidence-based judgement is checked as before.

- **`treeship judge --format json` prints `reason_facts`:** the same answers as Zerker Reason premises under the `model-judged` authority class, one per question, with the signed receipt as the fact id. Reason's side (the class convention, the example program and its tests) landed in zerkerlabs/reason#21.
- **The judge slot, with a deterministic first judge.** `treeship judge` asks a judge typed questions about a tool call (`noul`, `choice`, `score`), holds the answers to a threshold, and with `--attest` signs each as a `judgement.v1` chained onto the session. The built-in judge is `treeship-rules`: pattern rules over the call (a path outside the workspace, a shell command that destroys or exfiltrates, a host outside the declared network scope, an amount above a bound) answered with probability 1 or 0 and replayable by a verifier, so no model is in the decision path unless the operator points at one. `--judge-url` sends the same request to any HTTP judge that speaks the contract (a decision model, an LLM judge, a classifier) and holds its answer to the same checks: every question answered in its type, every probability in range, an unavailable judge an error and never an allow. The Claude Code gate opts in with `TREESHIP_JUDGE=1` or `TREESHIP_JUDGE=<url>`, after the card and never instead of it: an answer over the bar denies with a `blocked.v1` (`policy_threshold_exceeded`) naming the judge and the questions, `ask` asks the operator, and a judge that cannot answer fails open with a note in the timeline. The gate's halt refusals now chain onto the session too.
- **The kill switch reaches the bridges.** `treeship halt` stopped the Claude Code plugin and nothing else; an agent on the MCP bridge or behind the A2A middleware kept working while the halt stood, and the halt page claimed otherwise for strict mode. The MCP client now asks `treeship halt list` before every `callTool` and, under a halt this ship signed against its actor (or `*`), refuses before the server sees the call and throws `TreeshipHaltedError`. The A2A middleware refuses in `admitTask` (`halted`, before the presentation is read) and in `onTaskReceived` (local tasks too). Every refusal is signed as the same `blocked.v1` the plugin mints, chained onto the session with `--chain`. A check that cannot run fails open and is said once on stderr, as the plugin does; under `TREESHIP_STRICT=1` the bridges refuse instead. `TREESHIP_A2A_UNVERIFIED=1` never skips a halt.
- **The gate reads the card `onboard` writes.** `treeship onboard --tools …` minted a signed card carrying the tools and left the local card record, the file the Claude Code gate actually reads, at empty capabilities, so an agent onboarded the documented way had every tool call refused as off-card. `onboard` now passes the tools to registration and copies the signed card's full tool set (declared, captured from a harness, discovered from an A2A card) onto the record. The gate end-to-end test covers the onboard path.
- **A recipient reaches `proven (key-bound)`.** Actor proof consulted only the local agent registry, so on any other machine an agent's action graded `asserted` however many pins the verifier held. `verify` now also walks the signed `agent_cert.v1` in the store: a certificate that binds the actor to the signing key, signed by a key pinned under `cert_issuer`, inside its validity window, proves the binding. Without the certificate the grade stays `asserted`, and the docs say which pins a counterparty needs today: `cert_issuer` for resolve, plus the agent's `agent_cert` for import.
- **Rotation is local, and says so.** `keys rotate` mints a successor in this keystore and nothing else: no succession artifact travels, and a pin has no expiry, so counterparties keep trusting the predecessor and cannot verify the successor until they re-pin. The command now prints that, with the export lines to send and the `trust remove` to ask for; the trust-model and keys pages no longer claim verifiers can walk a rotation chain.
- **A handoff reports the work it names.** `verify` on a handoff prints how many named artifacts are present in this store and lists the ones that are not, with a warning that the handoff envelope verifies on its own and vouches for nothing it does not carry. The handoffs guide shows the real output and the real `trust add` (a key id, not a label).
- **`trust add` refuses a label where a key id is matched.** Pins for `cert_issuer`, `revoker`, `agent_cert` and `session_host` are matched against the signature's key id; a pin under a label never matched anything and looked pinned. Those kinds now require `key_<16 hex>` or `key_agent_<16 hex>`; `--label` carries the name. Hub kinds keep free-form ids.
- **`bundle import` names the key and the fix.** An unverified envelope now says which key signed it, the exact `trust add` line to run (from the producer's `keys export`), and which kind an agent-signed versus ship-signed envelope needs. The bundle page describes the real export (signed envelopes, no public key in the file).
- **Every power `keys export` prints is explained.** The ship key exports four pin lines; each now carries a comment saying what it grants, and `revoker` is called out as the power to revoke cards on the counterparty's machine, handed over deliberately. `onboard` explains why both the ship pin and the agent pin are needed today, and which survives a rotation.
- **A revocation names its signer.** `verify-capability` said `issuer (ship) revoked` for any pinned revoker; it now says `self-revoked (the card's own key)` or `pinned revoker key_… (a key this machine pinned under --kind revoker)`, and the capability-cards page uses the real kind.
- **An ambiguous artifact prefix is reported at any length.** `art_c` naming twelve artifacts now says so and lists candidates (first ten) instead of `not found`.
- **Git reconcile skips `.treeship/` whole.** Every file under the project's Treeship directory is written by the CLI or a hook, never by the agent's work; the receipt named `declaration.json` and card records as the agent's writes. The runtime-artifact list is gone.
- **`session mint-challenge` prints the outside-verifier pair** (`present --challenge` and `verify-presentation --challenge`) alongside the room-join commands, and the handshake page mints its nonce with the CLI.
- **`treeship agents` is visible in `--help`** and the generated command matrix.
- **The MCP bridge page says when its artifacts chain.** Intent and receipt artifacts chain onto the session only when the session's actor is the bridge's; otherwise a `chain_completeness` warning is expected and means what it says.
- **A closed stdout no longer aborts a command.** `treeship onboard | head -1` died with a panic after registering the agent and before minting its card. Output writes now ignore a closed pipe; every step runs and the exit code is the command's own.

- **Retries as a signed chain.** A trace that cannot explain a retry is not observability: attempt two of a flaky call used to be a sibling of attempt one, and a verifier could not tell "recovering from a timeout" from "did the same thing twice". `attest action --retry-of <id> --attempt N --retry-cause <timeout|error|rate_limited|operator|unknown> --backoff-ms <ms>` signs a `retry` block into the statement (v1 and v2), with the idempotency key sent, so the reason is under the signature and older receipts keep their bytes. `package verify` gains a `retries` row that walks every chain: same action and actor, attempts counting up, the same key on both sides, the retried attempt present in the package, and no two attempts that each report a distinct effect; a chain that fails any of those is named. The feature is now on by default in every published binary; `--no-default-features` removes it and the commands say so. Nothing is exported until `TREESHIP_OTEL_ENDPOINT` is set. Export requests now carry a five-second timeout, so a collector that is down or slow costs seconds and never fails a close. The otel page now matches the binary: `status` and `export` output as printed, endpoint required with no default, export enabled by default once the endpoint is set, and close exporting the `session.close` artifact's span rather than "all artifacts". CLI tests send a span to a local one-shot collector and close a session against a dead endpoint.
- **A kill switch: `treeship halt`.** `treeship halt agent://<name> --reason "…"` (or `treeship halt '*'`) signs a `halt.v1` receipt, chains it onto the active session and writes a marker; the Claude Code plugin's PreToolUse gate then refuses every tool call for that actor, before any card rule, and signs each refusal as `blocked.v1` with `operator_revocation`. `treeship halt --lift <actor>` signs the lift and clears the marker; `treeship halt list` shows what stands. Both orders are sealed into the package, so a verifier sees when the switch was thrown, by whom, and when it was lifted. A marker with no signed artifact from this workspace is reported as ignored and not honoured. It reaches what the hooks route; a process an agent started outside them is not stopped, and the docs say so.
- **Receipts in pull requests: `session close --receipt-dir`, the `Treeship-Receipt` commit trailer, and a `verify-receipts` GitHub Action.** `.treeship/` is gitignored almost everywhere, so a sealed session package never reached the pull request it accounted for. `session close --receipt-dir <DIR>` copies the sealed package (with `record.json`) into a directory you commit, and close now prints a git trailer, `Treeship-Receipt: <session_id> sha256:<digest of receipt.json>`, to paste on the commit; JSON output adds `receipt_digest`, `commit_trailer` and `receipt_copy`. The composite action at `.github/actions/verify-receipts` installs a pinned `treeship`, runs `package verify --strict` on every package in the checkout against a trust roots file the repository commits, cross-checks the trailers on the PR's commits against `sha256(receipt.json)`, writes a step summary with one row per package, and fails on any verdict other than `verified`, on a trailer mismatch, and, with `require: true`, on a PR with no packages; a PR with no packages otherwise says "0 packages" and warns, never a bare green. This repository runs it on itself (`receipts.yml`, `receipts/trust_roots.json`). Guide: [Receipts in pull requests](docs/content/docs/guides/receipts-in-pull-requests.mdx).
- **Fix: a package closed by an agent with its own key did not verify on another machine.** `session close` signs the `session.v1` close record with the actor's own key when the actor has one, and wrote it into the package after `keys.json` had already been composed from the chain's signers, so the package named every signer except the one on `record.json`. On the producing machine the key came from the local keystore and the package verified; on any other machine `receipt_binding` failed with "a key the package does not carry". Close now adds the record signer's public key to `keys.json`. Found by the verify-receipts check on the first package this repository committed. Regression test verifies such a package strictly from a second, fresh workspace.
- **The verdict invariant, as one suite.** *No green verdict is reachable without signature verification against a key the verifier trusts.* Three advisories in four months (v0.10.4, v0.19, v0.31.2) shared that root cause and each got a test for its instance; `verdict_invariant_cli.rs` is the test for the class: eight verdict-printing commands (`verify`, `verify-capability`, `verify-presentation`, `verify-profile`, `package verify`, `session report`, `workflow verify`, `vi verify`) against flipped payloads, stripped signatures, unknown keys, forged ids, reordered chains, emptied packages and unpinned roots, each on its own copy of a real workspace, asserting a nonzero exit and no green verdict on either the text or the JSON surface. It runs as its own workflow with a badge. Write-up: [docs/security/verdict-invariant.md](docs/security/verdict-invariant.md).
- **Two false greens the suite found, fixed.** `verify-capability` on a card whose envelope had its signatures stripped exited 0 and printed a check mark, because "no valid signature" was folded into the self-asserted grade; it now fails closed for an unsigned card or one no key this machine trusts can verify, and re-derives the id from the signed bytes. `vi verify --local --require-attestation` checked that the attestation artifact existed, not that it verified, so a flipped byte in the stored record still passed; it now verifies the attestation's signature under a trusted key, re-derives its id, and does the same for every artifact in the walked chain (`local_chain_signatures` row).
- **The Claude Code plugin gates tool calls on the agent card.** A `PreToolUse` hook reads the session actor's registered card (`treeship agent register --tools/--forbidden/--escalation`), maps Read/Write/Bash/WebFetch/Agent and `mcp__server__tool` onto the card's capability names, and denies a forbidden tool with a signed `blocked.v1` receipt (`scope_violation`), asks the operator for an escalation tool, allows a bounded one, and records an off-card call as an `agent.note` unless `TREESHIP_GATE=enforce` turns it into a refusal. A refusal is an artifact sealed with the session, not a log line. No card means no policy, and the hook fails open on every error. Parity fixtures cover all four outcomes; the mock `treeship` now answers `session status --format json` and the runner seeds cards from `fixtures/<plugin>/agents/`.
- **`evaluation.v1`: an evaluator's signed grade.** The pacing proposals that pair a capability checkpoint with a certification ("a model with capability X carries certification Y") need the certification to be a record a stranger can check. `evaluation.v1` is that record: what was evaluated (a model, agent, session or package, by digest), with which suite (by digest), in which environment, and what the evaluator concluded, with `verdict` in `pass`, `fail`, `inconclusive` enforced before signing. Attested with `--subject` on the graded artifact, it chains onto the thing it grades. The docs state the self-asserted rule: a grade signed by the subject's own key is not independent.
## 0.31.5 (2026-09-17)

- **The receipt's agent graph is written, not only defined.** `agent.spawned` and `agent.returned` existed in the event vocabulary and the graph builder, and no producer emitted them: a session with subagents sealed with `spawned_subagents: 0` and no `parent_child` edge. `session event` now takes both types (`--agent-name` is the child; the parent rides in `--meta` as `spawned_by`, the return target as `returned_to` or `--destination`), and the timeline prints them as `spawned` and `returned`. The Claude Code plugin adds `SubagentStart` and `SubagentStop` hooks that emit them, and its PostToolUse hook tags a subagent's tool calls with the subagent's instance name (`<agent_type>#<id>`) instead of the parent's, so the sealed receipt says which instance did what.
- **Two predicates for inference verification: `verification.packet.v1` and `verification.recompute.v1`.** The AI Futures Project's verification plan asks for AI workloads to be cut into discrete packets that a recomputation server can spot-check, and lists the integrity of what that server reports back as unexplored. These predicates are the record layer for that scheme. A prover signs a packet receipt (model, input and output digests, stream position, an optional reproducibility claim); a verifier signs a recompute receipt about it with `--subject` set to the packet, so the result chains onto the claim it checks and `verify` walks from one to the other. `verdict` is `match`, `mismatch` or `inconclusive` and anything else is refused before signing; `method` is free-form so DiFR, TOPLOC or bit-exact schemes need no registry change. Treeship does not do the recomputation and claims nothing about reproducibility; it makes the reports signed, chained, and verifiable offline by the other side. Guide: [Verification reporting](docs/content/docs/guides/verification-reporting.mdx).
- **Retest of 0.31.4, the four items left open.** `attest receipt --subject <external ref>` no longer records the subject as a storage parent, and the chain walk stops at a parent that is not an artifact id, so `verify last` passes on a receipt about `ord_12345` (FR-4, the receipt half). `session report --format json` exits nonzero on a failed local verify on every path, including no hub attached, and nonzero on an upload error; the no-hub message no longer says the receipt verifies locally beside `verification_status: fail` (FR-7). `verify-presentation` prints a pin command with a real root name instead of `<name>`, and when the card's signature is unpinned it names the signing key id and the `keys export` line to ask the producer for (FR-5). The default `--parent` inside a session is scoped to the session's actor: another agent's receipt in the same workspace is sealed loose unless it passes `--parent` on purpose (P3).
- **Release: the npm landing wait asks for the exact version and waits fifteen minutes.** `wait-for-npm-version.sh` compared the `latest` dist-tag, which npm's CDN updates minutes after the version itself, and gave up after five; on 0.31.4 it split the release across npm twice. It now asks whether `<pkg>@<version>` is installable, for up to 900 s.

## 0.31.4 (2026-09-11)

- **The sealed set is under a signature (audit follow-up AUD-34, P1).** An artifact from another session, signed by the same key, could be dropped into a package as an `unchained` entry with the tree recomputed, and every per-artifact row stayed green, `--strict` included. `session close` now seals its `session.v1` record beside the package as `record.json`; that record signs the SHA-256 of `receipt.json` and the session id, so `package verify` gets a `receipt_binding` row that fails when the sealed set was rewritten after the producer closed it. A `session_window` row warns when a sealed artifact's signed timestamp falls outside the session's own window. Under `--strict`, `chain_completeness`, `receipt_binding` and `session_window` are failures. A package built before this release has no record and gets a warning. A producer who re-signs is outside what a signature can catch; that is what checkpoint anchoring is for.
- **`package verify` says `signatures-pass`, not `verified`, when no signing key is pinned (AUD-35, P2).** The success line and the JSON `verdict` distinguish `verified` (every signature under a pinned key), `signatures-pass` (signatures verify, signer not pinned here), `structural-pass` and `failed`. `--format json` now carries every check row, the counts, and `signer_pinned`; it carried no rows at all before.
- **`attest action` chains onto the session's head by default (P3).** Every documented quickstart omits `--parent`, so every session's own actions were sealed as `unchained` and `chain_completeness` warned on honest sessions. Inside an active session the parent now defaults to the newest artifact that walks back to the session root; `--no-parent` keeps a receipt deliberately off the chain. `session close` chains onto that head too, instead of whatever `.last` held, so another agent's receipt in the same workspace no longer becomes the session's chained step.
- **The MCP bridge's `TREESHIP_STRICT=1` reaches the caller (AUD-33 residual).** The client caught every throw from the attestation module; a signing failure under strict now fails the tool call, and a test drives it through `callTool`.
- **`verify last` on a receipt with an external subject** (`ord_12345`) no longer walks to the subject as if it were a chain parent (FR-4). **`session report` exits nonzero when its own local verify failed** (FR-7). **`session event --help` lists every event type** and says `agent.decision` requires `--model` (FR-9).

## 0.31.2 (2026-09-10)

- **`package verify` checks signatures (audit 2026-09 AUD-31, P1; advisory [TS-2026-002](docs/security/TS-2026-002.md)).** Through 0.31.1 the command verified the Merkle tree and nothing under it: a receipt whose sealed set was rewritten to an invented `art_` id, with the tree recomputed, verified with exit 0. A `.treeship` package now carries the signed DSSE envelope of every sealed artifact under `artifacts/` and the signing public keys in `keys.json`, and `package verify` verifies each envelope's Ed25519 signature against those keys, re-derives the content-addressed id and digest from the signed bytes (`signature:<id>`), checks that every chained artifact names the previous one as parent inside the signature (`chain_linkage`), and reports whether the signing keys are pinned trust roots (`signer_trust`, a warning with the exact `treeship trust add` command; a failure under `--strict`). A fabricated id, an edited byte, a reordered chain, or a missing key fails with a nonzero exit. Packages built before 0.31.2 carry no envelopes and fail at a new `envelopes` row; `--structural` reads their structure and approvals with a verdict that says signatures were not checked. Core: `verify_package_with_options`, `verify_package_structural`, `PackageKeys`.
- **`session close` seals unchained artifacts (AUD-32, P1; QA TS-002b).** An `attest action` signed without `--parent`, or onto a parent off the sealed path, was absent from the package while `package verify` reported it clean; three such actions in one session left one in the receipt. Every artifact signed in the workspace during the session is now sealed, after the chain, and marked `unchained: true` in the receipt so a verifier can tell a linked step from a loose one; the close output lists them (`sealed_unchained` in JSON, a warning and hint in text) and `package verify` reports them as `chain_completeness`. `attest action` prints a hint when a session is active and no `--parent` was given.
- **The MCP bridge reports signing failures (AUD-33, P2).** A failed `attest`, `session event` or `session start` inside the bridge was caught and dropped, so a tool call with no receipt looked like one that was never recorded. The bridge now writes `[treeship] <what> failed: <reason>` to stderr on every failure and, under `TREESHIP_STRICT=1`, fails the tool call instead of proceeding unrecorded.
- **Docs: the Verifiable Intent page says which draft.** "Shipped in 0.31" is qualified as shipped against the v0.1 draft, the wording the CLI uses (QA TS-007). The commerce quickstarts start from `git clone` of the reference (QA TS-008).

## 0.31.0 (2026-09-08)

- **`treeship vi`: Verifiable Intent credentials, shipped.** An independent implementation of the Verifiable Intent v0.1 draft (verifiableintent.dev, Mastercard-maintained, Google co-developed) in `treeship-core::vi`, with a CLI: `vi keygen` mints the agent's P-256 key (sealed by the ship keystore) and prints the JWK a wallet binds under `cnf`; `vi check` asks whether a purchase fits a Layer 2 mandate; `vi attest` signs the Layer 3 pair (L3a for the payment network, L3b for the merchant) as key-bound SD-JWTs with `sd_hash` over recipient-specific L2 presentations and `transaction_id == checkout_hash`, refusing anything outside the mandate before signing; `vi verify` runs the reference verifier's checks plus the Treeship attestation and, with `--local`, the chain it names. The spec's optional `agent_attestation` claim carries a `treeship.receipt-chain.v1` value: a ship-signed statement, stored as an artifact chained onto the head, naming the session, chain head, Merkle checkpoint, approval use, mandate digest and transaction. Interop is tested both ways against the reference SDK in CI (`tests/vi-interop`): the reference's `verify_chain` and `check_constraints` accept what treeship signs and ignore the claim as the spec requires; treeship verifies what the reference issues; one edited byte fails on both. `packages/vi` (April 2026 types against a pre-v0.1 draft, never wired) is retired; the code lives in `packages/core/src/vi/`. The eight registered constraint types are checked with the reference checker's semantics. Not in scope: multi-pair L2 mandates, network-side cumulative budget and occurrence counting.

- **treeship-commerce: the approval verdict next to the tool outcome.** `TreeshipApprovalMixin` now sets `treeship_last_approval` (`proven`, `unproven`, or `None`) on the executor after every apply, so a host can print or log what the intent receipt says about the grant beside what the tool did. `demo_merchant` uses it: the replay row reads `error, approval unproven` in the default run (the journal refused a second use before anything was signed; the mock backend then refused the apply as already applied) instead of a bare `error` that let the backend take credit for the journal's refusal. Under `--enforce` the row is unchanged, `blocked:approval`.
- **Docs: verify a session package**, a page for the person handed a `.treeship` package (`/commerce/verify-a-package`): what each check proves and does not, the counterparty signature flow (`keys export` → `trust add` → `bundle import` → `verify`), and the limits (`anchoring: UNWITNESSED`, `actor proof: asserted`, `--require-authority` on receipts with no mandate). Shopping demo recording added to the integration page and the announcement post.
