# TS-2026-002: Session packages verified structure, not signatures

| Field             | Value                                                        |
|-------------------|--------------------------------------------------------------|
| **Identifier**    | TS-2026-002                                                  |
| **Title**         | `treeship package verify` accepted a sealed set with fabricated artifacts; `session close` dropped unchained artifacts from the sealed receipt; the MCP bridge swallowed signing failures |
| **Affected**      | `treeship` CLI and `treeship-core` `<= 0.31.1` (`package verify`, `session close`); `@treeship/mcp` bridge through the same release |
| **Fixed in**      | `treeship` `0.31.2`                                          |
| **Severity**      | High (AUD-31, AUD-32: P1); Medium (AUD-33: P2)               |
| **Discovered by** | Internal security review, 2026-09-09, against `d9159790` (0.31.1). Findings AUD-31, AUD-32, AUD-33 |
| **Public disclosure window** | None. Fix shipped in the release after discovery. No field exploitation observed. |

## Summary

A `.treeship` session package is the artifact Treeship tells a stranger to
verify. Through 0.31.1, `treeship package verify` checked that the package
was internally consistent (the receipt parses, the Merkle root recomputes
over the listed ids, every inclusion proof verifies, the timeline is
ordered) and stopped there. It never verified an artifact envelope's
Ed25519 signature and never required the envelope to exist. A receipt
whose sealed set was rewritten to an invented `art_` id, with the tree
recomputed to match, verified with exit 0 and a green verdict (AUD-31).

Two adjacent findings compound it. `session close` sealed only the
artifacts reachable along the parent chain from the close artifact, so an
`attest action` signed without `--parent` was signed, stored, and absent
from the package while `package verify` reported it clean; three such
actions in one session left one in the receipt (AUD-32). The MCP bridge
caught every `treeship` failure inside a tool call, returned `undefined`,
and printed nothing unless `TREESHIP_DEBUG=1`, so a call that was never
recorded looked to the caller like one that was (AUD-33).

`treeship verify <id>` was not affected. It performs real DSSE
verification: a one-byte edit to a stored envelope fails with `invalid
signature for key …` and exits 1, and the audit confirmed it. The
documentation for the verifier guide said, correctly, that the package
proved structure and the bundle proved signatures; the gap is that the
verdict line did not say so, and the package format made a signature
check impossible from the file alone.

## Affected versions

- `treeship` and `treeship-core` through `0.31.1`, every release that has
  had `package verify` (since 0.9.x). The structure-only behaviour was the
  design from the start, not a regression.
- `@treeship/mcp` through the release shipped with `0.31.1`.

## Fixed in

`treeship` `0.31.2`.

**AUD-31.** A package now carries the signed DSSE envelope of every sealed
artifact under `artifacts/<id>.json` and the signing public keys in
`keys.json` (`treeship/package-keys/v1`, key id to `ed25519:<base64url>`).
`package verify` verifies each envelope's Ed25519 signature against those
keys, re-derives the content-addressed id and the digest column from the
signed bytes (`signature:<id>`), checks that every chained artifact names
the previous one as `parentId` inside the signature (`chain_linkage`), and
reports whether the signing keys are pinned trust roots (`signer_trust`:
a warning carrying the exact `treeship trust add` command, a failure under
`--strict`). A fabricated id, an edited byte, a reordered chain, a missing
envelope, or an unknown key fails with a nonzero exit. Packages built before
0.31.2 carry no envelopes and fail at a new `envelopes` row whose message
says why; `--structural` reads their structure and approvals with a
verdict that says signatures were not checked. In `treeship-core`:
`verify_package_with_options(pkg, trust, structural_only)`,
`verify_package_structural(pkg)`, `PackageKeys`.

**AUD-32.** Every artifact signed in the workspace during the session is
sealed, after the chain, and marked `unchained: true` in the receipt so a
verifier can tell a linked step from a loose one. The close output lists
them (`sealed_unchained` in JSON, a warning and a hint in text), and
`package verify` reports them as `chain_completeness`. `attest action`
prints a hint when a session is active and no `--parent` was given. The
0.31.1 `unsealed_branches` report, which covered forks whose parent was on
the chain, is unchanged; forks are now sealed too.

**AUD-33.** The bridge writes `[treeship] <what> failed: <first line of
stderr>` on every signing failure, unconditionally, and under
`TREESHIP_STRICT=1` fails the tool call instead of proceeding unrecorded.

## What a verifier should do

- Re-run `treeship package verify` with 0.31.2 or later on any package you
  accepted on the strength of a green verdict. A package built before
  0.31.2 will fail at `envelopes`; its artifacts can still be verified from
  a bundle or the hub with `treeship verify <id>` after pinning the
  producer's key, as the [verifier guide](https://docs.treeship.dev/commerce/verify-a-package)
  has always described.
- Pin the producer's key (`treeship trust add <key_id> ed25519:<pk> --kind cert_issuer`)
  before reading `signer_trust` as anything but a warning. The package
  names its keys; it cannot vouch for them.
- Ask producers to re-close sessions that matter with 0.31.2 so the
  package carries its envelopes.

## What a producer should do

- Upgrade to 0.31.2. Sessions closed after the upgrade carry every signed
  artifact and its envelope.
- Chain receipts with `--parent`. An unchained receipt is now sealed, but
  its order is your unsigned claim, and `chain_completeness` will say so.
- If you run the MCP bridge in a setting where an unrecorded call is worse
  than a failed one, set `TREESHIP_STRICT=1`.

## Reproduction

`docs/security/audit-2026-09-repro.sh` builds the CLI from source, runs the
three findings in an isolated workspace under `target/`, never touches
`~/.treeship`, and prints one line per finding. On `d9159790` it reports
AUD-31 with exit 0 and AUD-32 with two of three actions dropped; on the fix
it reports exit 1 and zero dropped. Regression tests:
`packages/core/tests/package_signatures.rs`,
`packages/cli/tests/session_unsealed_branch_cli.rs`,
`bridges/mcp/test/attest-failure.test.ts`.
