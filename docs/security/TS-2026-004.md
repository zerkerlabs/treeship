# TS-2026-004: `package verify` could report a rewritten receipt as verified, and workspace writes followed symlinks

|-------------------|--------------------------------------------------------------|
| **Identifier**    | TS-2026-004                                                  |

## Summary

### 1. Package verification could report a rewritten receipt as verified

A session package carries a close record (`record.json`), signed at close, that binds the digest of `receipt.json`: the session name, narrative, timeline and side effects. Before 0.31.10 the verifier accepted a close record signed by **any key listed in the package's own `keys.json`**. An attacker who held no key of the producer's could:

1. Rewrite `receipt.json`.
2. Add a key of their own to `keys.json`.
3. Sign a new close record over the new digest.

`package verify` and `package verify --strict` then reported `verified`. The artifacts' own signatures still verified, so the evidence itself was intact, but the receipt text a reader sees was not.

A second, related weakness: a package with no artifacts and no close record was reported `verified` by default, because the verdict came from the absence of failures rather than from checks that passed.

The published advisory covers a broader set of related weaknesses fixed in the same release (a key id could be re-pointed at a different key; the approval-use limit was read from an unsigned field) -- see the GHSA linked above for the complete list. This page covers the close-record binding defect specifically.

### 2. Workspace writes followed symbolic links

`treeship init` and other commands wrote under `.treeship/`, and into the working directory, through symbolic links and predictable temporary file names. A malicious repository could make `treeship init` overwrite files outside the workspace (for example `~/.ssh/authorized_keys`), write key material to a location it chose, or have its journal moved into the user's global workspace.

## Fix

**Item 1 (close-record binding):**

- The close record must name the session's own sealed `session.close` artifact. The package must contain exactly one such artifact for the session. It must be chained, and its signer must equal the signer of the chain-root `session.start`.
- The record must be signed by that close's signer, or by a record key that close names inside its signed payload. The verifier's trust store plays no part in this binding.
- When a package mixes trusted and untrusted signing keys, it fails.
- Approval envelopes are judged in their own row. An unpinned approver caps the verdict at `signatures-pass`.
- `verified` and `signatures-pass` now require explicit passing rows. An empty package fails.
- `treeship verify <package>`, the dashboard and `session report` use the same verdict as `package verify`.

**Item 2 (symlink-following writes):**

- Every write under `.treeship/` and into the working directory opens with `O_NOFOLLOW`, sets the file mode at creation, and uses exclusive random temporary files.
- Hard-linked files are replaced, not written through.
- A symlinked path component below the workspace root is refused.
- A discovered project config can't point key or artifact storage outside the project, and only the user's own legacy journal is ever migrated.

**Residual limits (item 2):** intermediate directories are checked and then opened by path; `openat`-based walking is planned. On Windows, protection is check-then-open only.

## Behaviour changes

- A package closed by an agent's own key on 0.31.9 or earlier doesn't name its record key. It now fails `receipt_binding` by default. `--structural` reports what can still be checked; that verdict is structural-pass, never verified.
- An envelope-carrying package (0.31.2 or later) with no close record fails by default (W1-4, released together with this fix).
- An approver or agent key now needs to be pinned for `verified`, unless the session's own close names it.

## What to do

- Upgrade to `0.31.10`.
- Re-verify any package you accepted as `verified` from a party you don't control.
- Use `package verify --strict` in CI.
- On older versions, don't run `treeship init` inside a repository you don't trust.
