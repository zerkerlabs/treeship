## Summary

### 1. A trusted party's key could stand in for another agent

The agent-card checks share one question: is this card key-bound, meaning signed by the agent's own pinned key? That check had three weaknesses.

- **Signer taken from an unverified field.** The signer was read from the envelope's first `signatures[].keyid`, which is not verified. The signature check itself passes when *any* signature on the envelope verifies against *any* trusted key. So a party whose key the verifier already trusted could do this:
  1. sign a card for another agent with its own key
  2. add a second, invalid signature entry naming that agent's key
  3. have the card graded as key-bound to that agent

  The same applied to revocations. A forged revocation could mark an agent's real card revoked. In `resolve`, a revocation of a different card counted against this one.
- **Agent pins didn't name an agent.** An `agent_cert` trust root recorded a key but not which agent it belonged to. Any agent key the verifier had pinned could sign a card claiming any other agent's name, and it verified as key-bound. `treeship verify` accepted a self-signed agent certificate the same way to prove an action's actor.
- **The newest card won.** `resolve` picked the agent's newest card by its self-declared `signed_at`, among any card a trusted key verified. The hub served only one revocation per card, chosen the same way. A newer forged card, or a later forged revocation, could therefore hide a real revocation, so a revoked agent read as live.

**Precondition:** the attacker holds a key the verifier already trusts. That means any trust-root kind for the first weakness, and an `agent_cert` pin for the second. A party with no trusted key can't use any of this.

### 2. The preview and certificate pages did not escape every field

The receipt preview (`preview.html` in session packages, and the online preview at `/receipt/<id>/preview`) and the certificate page from `treeship present` escaped `&`, `<` and `>` but not quotes. Some count-shaped fields and the render-error text were inserted without escaping at all. A crafted receipt or card could therefore place markup in the page.

The online preview has served a strict content-security policy since 2026-09-28: a script hash plus a sandbox with an opaque origin. That kept injected markup from running there before this fix.

## Fix

**Item 1:**

- A card is key-bound only when its own key is among the signatures that **verified**, and that key's `agent_cert` pin names the card's agent.
- `agent_cert` pins carry an agent scope. It's set with `treeship trust add … --kind agent_cert --agent <uri>`, and written by `agent register`, `onboard` and `keys export`.
- Agent URIs have one canonical spelling. `--replace` is required to change a pin's scope.
- `resolve` (local and `--hub`) picks the current card among the agent's key-bound cards.
- The hub serves every revocation for a card.
- A revocation is honoured only when it verifies under the card's key or a pinned revoker, and names that card.
- A `compromised` revocation applies to every card of that key.
- `treeship verify`'s actor proof and certificate verification require the pin's scope to match.
- Verdicts carry `key_bound_reason`.

**Item 2:**

- One escaper covers quotes in both pages.
- Count-shaped fields are coerced to numbers.
- Timestamps and error text are escaped at the source.

## Behaviour changes (action required)

- **`agent_cert` pins without an agent scope no longer bind cards.** This covers every counterparty pin created from a 0.31.11-or-earlier `keys export` or `onboard` line. Their cards grade as asserted, and `resolve`, `verify-capability` and `verify-presentation` print the exact fix:

  ```
  treeship trust add <key_id> <pubkey> --kind agent_cert --agent <agent-uri> --replace --yes
  ```

  Pins written by `agent register` on your own machine keep binding.
- If you believe a key is compromised, revoke with reason `compromised` and remove it from trust with `treeship trust remove <key-id>`. Removal is the definitive answer.

## Recommendation

1. Upgrade to 0.31.12: the CLI, `@treeship/verify`, `@treeship/sdk`, `@treeship/core-wasm` and `treeship-core`. **If you run your own hub, upgrade it too:** a hub before 0.31.12 serves one revocation per card, so `resolve --hub` against it can still miss a real revocation that a later forged one hid. `api.treeship.dev` runs 0.31.12.
2. Re-pin counterparty agent keys with `--agent`, using the command the CLI prints.
3. Re-check any agent resolution or presentation you accepted from a party that shares your trust store.
